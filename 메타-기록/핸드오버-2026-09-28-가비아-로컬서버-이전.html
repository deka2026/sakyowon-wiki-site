핸드오버 2026-09-28 — 가비아 VPS 해지와 완도 B호기 로컬서버 전환

세션 요약

이사장님이 가비아 VPS를 해지하고 사교원 서버 전체를 완도 사무실의 로컬 서버(B호기)로 옮기셨다. 이 세션에서는 그 결과를 전수 실측해 구조를 확정하고, 그동안 여러 세션에 걸쳐 엇갈리게 기록돼 있던 기계 이름과 배포 경로를 바로잡았다. 결론부터 말하면 모든 호스트가 B호기 한 대에서 나가고 있으며 전부 정상이고, 데카가 배포까지 직접 수행할 수 있다.

확정된 구조 (2026-09-28 11:20 실측)

가비아 VPS(1.201.116.225)는 09-28 03:40 해지되어 기계 자체가 없다. SSH 22번 포트가 무응답인 것으로 확인했다. 월 약 8만 4천원이 절감된다.

현재 모든 서빙은 완도 B호기 한 대에서 나간다. 앞단은 Cloudflare Tunnel(cloudflared.service, root, active)이고, 터널 ingress 규칙은 로컬 파일이 아니라 Cloudflare 대시보드에 있다. 로컬에는 토큰만 있다(/etc/cloudflared/token).

아펙스 하위 경로도 전부 200으로 확인했다: /sakyowon-wiki/, /data, /academy-site/, /hatsoja/.

바로잡은 것 1 — 원점은 3호기가 아니라 B호기다

기존 메모리 project_sakyowon_hosting_2026q3 는 아펙스 원점을 “3호기 /opt/sakyowon/www/” 라고 적고 있었는데 틀렸다. 3호기는 대전에 있는 별개의 기계이고, 사교원 서버는 완도 B호기다. 두 기계는 테일스케일 주소부터 다르다.

원점 탐침으로 확정했다. 이 방법이 정본이다 — 헤더만으로는 구분이 안 된다(어느 쪽이든 server: cloudflare).

기계 정체를 확인하는 더 빠른 방법도 있다. systemd 유닛 설명에 이전 이력이 박혀 있다.

바로잡은 것 2 — 아펙스는 CF Pages가 아니라 터널이다

기존 메모리는 “터널 ingress 규칙이 6개뿐이고 아펙스는 없다 → 아펙스는 CF Pages 직접 업로드라 사교원 CF 토큰이 필요하고 그건 지미 몫”이라고 적고 있었다. 지금은 아니다. 09-28 09:17:57 에 터널 설정이 갱신되면서 규칙이 8개가 되었고, sakyowon.co.kr 과 www.sakyowon.co.kr 이 127.0.0.1:8041 로 추가됐다.

즉 아펙스 배포에 CF 토큰도 지미도 필요 없다. 데카가 직접 민다. 확인 명령은 다음과 같다.

바로잡은 것 3 — 위키 배포 절차는 무효가 아니다

메모리 project_infra_gabia_closed 는 wrap-up 4단계의 위키 배포 절차가 “가비아 자체서버 서빙 전제라 더 이상 안 맞는다” 고 적고 있었는데, 과했다. 사슬 자체는 살아 있고 마지막 한 칸만 바뀌었다.

  1. ~/workspace/sakyowon-wiki(비공개, quartz 소스)에 커밋·푸시
  2. node quartz/bootstrap-cli.mjs build → public/ 생성
  3. public/ 내용을 deka2026/sakyowon-wiki-site(공개, master)에 커밋·푸시
  4. 이사장님이 가비아에서 deploy-www.sh 실행 → 데카가 B호기에서 직접 실행

이 스크립트가 deka2026 의 레포 8개를 --depth 1 로 클론해 /opt/sakyowon/www/ 에 배치한다. 위키는 sakyowon-wiki-site@master → www/sakyowon-wiki 칸이다. 정상 종료하면 ===== 배치 완료 ===== 가 찍힌다.

⚠️ 배포 스크립트가 두 벌로 갈라져 있다

이 기계에 배포 스크립트가 두 개 있고 내용이 다르다. 다음 인스턴스가 엉뚱한 쪽을 실행할 위험이 있다.

경로시각성격
/opt/sakyowon/home/static/server/deploy-www.sh09:25정본. 레포 haeory-cyber/sakyowon-site 의 server/deploy-www.sh 를 sync 타이머가 1분 주기로 당겨온다. 소유자 보정 블록 있음
/opt/sakyowon/www-src/deploy-www.sh08:23갈라진 옛 사본. 레포 밖이라 버전 관리가 안 된다

옛 경로 /opt/sakyowon/src/deploy-www.sh(가비아 시절)는 존재하지 않는다.

두 벌의 차이는 서로를 보완하는 쪽이라 단순 삭제가 답이 아니다. 정본에는 소유자 보정 블록이 있지만 set -e 아래 git clone 이 맨몸이라 레포 하나만 클론에 실패해도 배치 전체가 중단된다. 옛 사본에는 그 실패를 건너뛰고 기존 내용을 유지하는 처리가 들어 있다. 정본 쪽에 그 내구성을 합쳐 레포에 푸시하는 것이 맞다.

레슨

  • “3호기”와 “완도 B호기”는 다른 기계다. 여러 세션이 이 둘을 섞어 적어 메모리끼리 충돌했다(같은 기계를 “3호기”·“완도 B”·“이 PC”로 제각각 불렀다). 기계를 지칭할 때는 별명만 쓰지 말고 테일스케일 주소나 hostname 을 함께 적어야 한다. 3호기는 대전, B호기는 완도 사무실이다.
  • 원점 판정은 추측이 아니라 탐침으로 한다. Cloudflare 뒤에서는 응답 헤더가 전부 같아서 어느 기계가 원본인지 구분되지 않는다. 위의 _origin-check.txt 방식이면 한 번에 끝난다. 이 방법을 몰라 앞 세션들이 “아펙스는 CF Pages일 것”이라는 추측을 사실처럼 기록했다.
  • 인프라가 바뀌면 옛 기록은 낡는 게 아니라 틀린 게 된다. 이번에 메모리 세 건에서 서로 어긋나는 서술을 발견했다. 낡은 기록을 남겨 두면 다음 인스턴스가 없는 기계에 SSH를 찌르거나(실제로 발생했다) 지미에게 필요 없는 부탁을 한다. 구조 변경을 확인했으면 그 자리에서 옛 기록을 고쳐야 한다.
  • 폐기 판정은 최소 단위로 한다. “가비아가 없어졌으니 위키 배포 절차 전체가 무효”라고 적혀 있었지만 실제로 바뀐 건 마지막 명령 한 줄이었다. 통째로 무효 처리하면 멀쩡한 절차를 다시 만드느라 시간을 쓴다.
  • 위키 소스(sakyowon-wiki)는 비공개지만 배포본(sakyowon-wiki-site)은 공개다. 기기 내부망 주소·SSH 계정명·키를 위키 본문에 적지 않는다. 그런 값은 스킬과 데카 메모리(로컬)에만 둔다.

미완료

  1. (데카) project_sakyowon_hosting_2026q3 메모리의 “3호기” 표기를 B호기로 정정하고, “아펙스는 CF Pages·지미 몫” 서술을 삭제한다. 이 세션에서 처리한다.
  2. (데카) project_infra_gabia_closed 메모리의 “위키 배포 절차 무효” 서술을 “마지막 명령만 교체”로 완화한다. 이 세션에서 처리한다.
  3. (데카) gabia-server-ops 스킬 앞머리의 배포 사슬 표를 위 실측값으로 갱신한다. 스킬 이름 자체가 이미 가비아 잔재이므로 개명(sakyowon-server-ops)을 검토한다.
  4. (확인 필요) 데이터 저장소 DB(/opt/sakyowon/data/datasets.db)가 가비아와 함께 사라졌는지 여부. project_infra_gabia_closed 에 “skdata tables 가 표 0개”로 적혀 있는데, 이후 project_sakyowon_data_store 는 “2026-09-28 완도 B 배포·라이브 검증 완료”로 적혀 있어 서로 맞지 않는다. 다음 세션에서 skdata tables 를 직접 실행해 판정할 것.
  5. (데카) 배포 스크립트 두 벌 정리. 정본(home/static/server/)에 옛 사본의 클론 실패 내구성을 합쳐 haeory-cyber/sakyowon-site 에 푸시하고, www-src/ 쪽은 그 뒤에 치운다. 레포를 거치는 변경이라 이 세션에서는 손대지 않았다.
  6. (이사장님) 가비아 계정에 남은 도메인·부가서비스가 있는지 확인. 서버는 해지됐지만 도메인 관리가 가비아에 남아 있을 수 있다.
