세션 요약

이사장님이 「사교원 서버를 통해 하는 작업에서 GPU 시스템을 얼마나 사용하는지」 물으셨다. 처음에는 서버 자체의 그래픽 장치를 재어 「GPU를 쓰지 않는다」고 답했는데, 여쭌 대상이 NIPA 고성능컴퓨팅 지원사업으로 배정받은 H200이었다. 신청서(서식_1_1)의 계획치와 실제 사용량을 대조해 실측했고, 이어서 아직 마운트되지 않은 채 개발만 끝나 있던 직원전용 질문 기능(staff_qa)을 라이브로 올렸다.

1. 사교원 서버 자체의 그래픽 장치 — GPU 사용 0

먼저 확인한 것은 완도 B호기 자체다. 결론은 서버 작업이 로컬 그래픽 장치를 전혀 쓰지 않는다는 것이다.

  • 하드웨어: Intel i3-13100(2코어 4스레드), WSL2에 메모리 9.7GB 할당, 외장 그래픽카드 없음. 그래픽은 CPU 내장 Intel UHD 730(공유 2GB)뿐이다.
  • CUDA와 ROCm이 설치돼 있지 않고, torch·tensorflow·onnxruntime·faster-whisper·transformers·llama.cpp·ollama가 하나도 없다.
  • WSL의 GPU 통로 /dev/dxg는 열려 있으나 그 장치를 여는 프로세스가 하나도 없다.
  • 윈도우 성능 카운터로 직접 재보니 전체 GPU 사용률이 1.49%였고, 그마저 전부 클로드 데스크톱 앱의 화면 그리기였다.

서버에서 도는 것은 cloudflared, sakyowon-www, sakyowon-home, sakyowon-api, deka-chat, sakyowon-talk, 그리고 Supabase 도커 컨테이너 11개다. AI 연산은 전부 외부(앤트로픽 클라우드 또는 품에 엔진)에서 돌고, 이 서버는 API를 왕복시키는 역할만 한다.

2. NIPA 고성능컴퓨팅 H200 — 계획과 실제

정본은 /mnt/d/사교원 개발그룹/서식_1_1_2026년_고성능_컴퓨팅_자원_이용_신청서_0422 (3).hwp이고, 같은 판의 PDF 사본이 /mnt/d/A-HDD-20260926/용역준비/에 있다.

여기서 확인해야 할 것이 하나 있다. 계획서에 적힌 GPU 시간은 전부 학습과 평가 몫이고, 서버 추론(서비스 운영) 항목이 아예 없다. 그래서 「사교원 서버 작업의 GPU 사용량」은 계획상 배정이 0이고, 실적을 적을 칸도 따로 마련돼 있지 않다. 중간점검 서면에서는 이 점을 전제로 칸을 나눠 써야 한다.

신청서는 베이스 모델을 EXAONE 4.5로 적었으나 실제 가동은 EXAONE 4.0 32B + LoRA v3다. 서류로 옮길 때 어긋나므로 주의한다.

사교원 서버가 GPU로 나가는 경로

GPU로 나가는 길은 좁다. 설정은 /opt/sakyowon/sakyowon-api.env의 POOME_API_BASE와 POOME_API_KEY이고, 서비스는 유저 유닛 sakyowon-api.service(포트 8787)다.

sakyowon.co.kr → :8787 sakyowon-api → chat.solarshare.kr/api/v1/ask → H200 EXAONE 4.0 32B v3

상담 탭(/api/ai/chat)과 경영진단 리포트(/api/consult/request)만 이 길로 간다. 서류·법령·번역 탭은 앤트로픽으로 직행하므로 GPU를 쓰지 않는다.

이 트래픽의 분류

09-29 오전 트래픽은 마을 10개·계정 22개·세션 213개가 08:53:52에 일괄 생성된 뒤 발생했고, 277건 중 214건이 단일 IP에서 3~10초 간격으로 들어왔다. 기계적 패턴이다.

이사장님 판단으로 이 부하는 「구축·검증」으로 분류한다. 실사용 직전의 통합 시험이며 시스템 구축에 반드시 필요한 작업이다. 서약서가 금지한 「AI 학습·추론과 무관하게 가속기 이용률만 과도하게 높이는 프로그램(GPU Burn 등)」과는 성격이 다르고, 승인된 연구·개발 목적 안에 있다. 실적에서 빼지 말고 「구축·검증」 항목으로 계상한다.

다만 정량목표 「실증 마을 3~5개」 칸에는 이 마을 10건을 올리지 않는다. 그 칸은 실제 참여 마을을 세는 칸이고, 시험 데이터를 넣으면 나중에 마을 명부를 요구받을 때 어긋난다. 두 칸은 별개로 관리한다.

3. 직원전용 질문(staff_qa) 라이브 — 2026-09-29 14:07

개발은 끝나 있었으나 마운트가 되지 않아 /api/staff/*가 전부 404였다. 이사장님 지시로 라이브에 올렸다.

올린 방법 — app.py를 고치지 않는다

app_staff.py 머리말에 이유가 적혀 있다. 2026-09-29 오전에 app.py에 직접 덧붙였더니 같은 시각 다른 작업이 그 파일을 통째로 다시 쓰면서 추가분이 말없이 사라졌다. 그래서 얹는 자리를 따로 둔다.

  • /opt/sakyowon/server/app_staff.py가 app.py에서 app, current_user, _poome_request, POOME_API_BASE, verify_pw를 가져와 staff_qa.configure(...)를 부르고 app.include_router(staff_qa.router)를 한다.
  • 유저 유닛 ~/.config/systemd/user/sakyowon-api.service의 ExecStart를 uvicorn app:app에서 **uvicorn app_staff:app**으로 바꿨다. 백업은 같은 폴더의 sakyowon-api.service.bak_20260929_prestaff다.
  • 이렇게 두면 app.py가 앞으로 어떻게 바뀌어도 이 기능은 살아남는다.

검증

전환 전에 이미 떠 있던 스테이징(포트 8051)과 라이브(8787)를 나란히 찍어 회귀를 먼저 확인했다. /api/auth/me, /api/villages, /api/consult, /api/my/village, /api/my/documents, /api/fed/dues, /api/monthly/summary, /api/ai/health 여덟 경로가 양쪽 모두 200으로 같았고, 차이는 /api/staff/status가 404에서 200으로 바뀐 것뿐이었다.

전환 후 공개 도메인으로 끝까지 왕복했다.

  • https://sakyowon.co.kr/api/auth/login으로 양양1 로그인 200
  • /api/staff/status 200 — 지식베이스 5,565문서·63,264조각(구축 2026-09-29 13:07), 엔진 exaone-lora 정상
  • /api/staff/ask 실제 질문 200 — 엔진 33.7초, 근거 8건을 인용한 답변. 클라우드플레어 100초 제한 안쪽이다.

라우트 10개가 모두 응답한다: status, ask, doc/plan, doc/plan_update, doc/section, doc/finish, docs, docs/{id}, docs/{id}/download, usage.

이 기능의 구조

  • 근거 찾기는 이 서버에서 한다. staff_kb.db(440MB)가 사교원 로컬 자료에서 개인정보가 지워진 조각을 골라 온다.
  • 글쓰기는 HPC 엔진(H200)이 한다. /api/v1/ask 한 곳으로만 나가고 앤트로픽으로 물러서지 않는다. 엔진이 쉬면 쉰다고 말한다.
  • 문서 만들기는 plan(목차) → section(절마다 한 번) → finish(합쳐 저장) 세 토막으로 나눠 부른다. 한 번에 문서 한 편을 다 쓰면 클라우드플레어 100초 제한에 걸려 524로 죽기 때문이다. 엔진 호출 제한초는 60으로 조여 있다.
  • 접근 권한은 역할 admin과 staff만이다. 직원 계정 임시 비밀번호는 0000이다(1111이 아니다).

GPU 사용량이 꺾이는 지점

질문 한 건에 엔진이 29.633.7초를 쓴다. 상담 탭(6.8초)의 45배다. 문서는 절 수만큼 더 부른다. 이 기능이 본격적으로 쓰이면 사교원 서버발 GPU 사용량의 자릿수가 바뀐다.

집계 창구도 함께 붙어 있다. **GET /api/staff/usage**가 {ask:{count, engine_ms, users}, doc:{count, engine_calls, engine_ms}, daily:[…]}를 돌려준다. consult_reports.engine_ms와 합치면 사교원 서버발 GPU 시간이 빠짐없이 잡힌다.

레슨

  1. 서버에 기능을 얹을 때 진입점을 따로 두면 덮어쓰기 사고를 피한다. 여러 작업이 같은 시각에 같은 파일을 만지면 나중 저장이 앞 저장을 말없이 지운다. app.py를 고치는 대신 app.py를 import하는 app_staff.py를 만들고 유닛의 ExecStart만 바꾸면, 본체가 어떻게 바뀌어도 기능이 살아남는다.

  2. 실서비스를 건드리기 전 여분 포트에서 먼저 띄운다. 이번에도 포트 8051에 스테이징이 떠 있어서, 전환 전에 라이브와 나란히 찍어 회귀를 먼저 볼 수 있었다. 경로별 응답코드를 표로 대조하면 「달라진 곳이 새 기능뿐」임을 눈으로 확인할 수 있다.

  3. 사용량을 물으면 세 칸으로 나눠 답한다. 계획(신청서 표), 전체 사용률(본부 배치분), 우리 몫(저널 건수 × 엔진 시간)이다. 섞으면 부풀리거나 깎이고, 지어낸 값은 환수 사유가 된다.

  4. 시간(720시간 분모)과 사용률(Util %)은 다른 축이다. 「계획 대비 50% 미만이면 사유서」와 「85% 이상이면 우수 인정」은 시간 기준이고, 15.9%는 연산 사용률이다. 같은 축에 놓으면 안 된다.

  5. 엔진 호출 시간은 DB에 남는 곳을 먼저 찾는다. 접근 로그에는 소요 시간이 없지만 consult_reports.engine_ms와 /api/staff/usage에는 건별로 남는다. 추정으로 답하기 전에 기록된 값이 있는지 본다.

  6. 엔진을 직접 부를 때 Authorization: Bearer를 같이 붙이면 403이 온다. 헤더는 X-API-Key만 쓴다(User-Agent는 선택).

  7. hwp5txt는 표를 떨군다. 신청서의 핵심 수치가 전부 표 안에 있어서 텍스트 추출로는 「<표>」만 나왔다. 같은 문서의 PDF 사본을 pymupdf로 읽어야 값이 보인다. 한국어가 사라지는 pdftotext 함정과는 별개의 문제다.

  8. check_status.py의 판정이 지금 오경보를 낸다. 2026-09-28에 /api/ai/chat에 로그인 필수가 걸려 401이 정상 응답이 됐는데, 스크립트는 그것을 고장으로 읽어 「연동 실패」로 찍는다. 판정은 /api/ai/health의 backend:"poome"로 한다.

미완료

  1. PMS 누적 사용시간 확인 — 실장. pms.cloudcompute.co.kr에 로그인해 이번 달 누적 사용시간을 읽고 방에 한 줄 남긴다. 「월 720시간 대비 50% 미만이면 사유서」를 판정하는 정본이고, 중간점검 서면에 반드시 들어가야 한다. 9/25 실행가이드의 0순위인데 나흘째 미수행이다.

  2. 직원전용 질문 화면 제작 — 데카 또는 보라. API 10개는 살아 있으나 www/ 어디에도 api/staff를 부르는 곳이 없어서 직원이 브라우저로 들어갈 문이 없다. 로그인 후 접근하는 직원 전용 화면이 필요하다.

  3. 지식베이스 검색 적중 개선 — 데카. 「망남신활력사업의 주요 사업 내용」을 물었더니 망남 관련 조각이 4,831개나 있는데도 엉뚱한 자료를 집어 「제공된 사교원 자료에는 없습니다」라고 답했다. 지어내지 않은 것은 정상 동작이지만, 이대로면 직원이 「우리 자료가 없다」고 오해한다. staff_kb.py의 검색을 손봐야 한다.

  4. check_status.py 오경보 수정 — 데카. 401을 unauthorized인 경우와 그 밖의 경우로 갈라 처리하고, 연동 판정의 1차 근거를 /api/ai/health로 옮긴다. 10월 중간점검 때 이 오판정을 그대로 믿으면 곤란하다.

  5. 스테이징 프로세스 정리 — 확인 후 누군가. 12:44부터 포트 8051에 떠 있는 app_staff:app 인스턴스는 라이브 전환으로 중복이 됐다. 다른 세션이 쓰고 있을 수 있어 이번 세션에서는 끄지 않았다.
